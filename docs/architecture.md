# Architecture

Structure of the DesignKit repo and the reasons for it. Rules digest: `CLAUDE.md`; recipes: workspace skill `design-system`. Details are settled by the specs in `docs/specs/`; this file states only what they build on.

## 1. Stack
- Swift package, swift-tools-version 6.2, Swift 6 language mode, strict concurrency; iOS 26, iPadOS 26, macOS 26
- SwiftUI + Observation; String Catalogs (pl default, en)
- Showcase apps generated by XcodeGen; SwiftLint as the quality gate
- No third-party dependencies

## 2. Layout
```
Package.swift
Sources/
  DesignKit/            Foundation only: DK data objects
  DesignSystem/         SwiftUI, every platform: tokens, theme, mds APIs, components
  MacDesignSystem/      AppKit-backed wrappers and macOS-only components
  PadDesignSystem/      UIKit-backed wrappers and iPad-only components
  PhoneDesignSystem/    UIKit-backed wrappers and iPhone-only components
DemoApps/
  project.yml           XcodeGen → Showcase.xcodeproj (generated, untracked)
  Shared/               catalog, pages, playground controls (every app)
  Phone/ Pad/ Mac/      app entry and platform pages
docs/
  architecture.md
  specs/{feature}/      specs and decisions; README index
  plans/{feature}/
```

## 3. Targets
| Target | Imports | Namespace | Holds |
|---|---|---|---|
| DesignKit | Foundation | `DK` | display-ready data objects Cores fill (`DK.ViewState`, `DK.ActionButton`, `DK.InlineAlert`, …); no tokens |
| DesignSystem | DesignKit, SwiftUI, ImageIO | `DS` (+ `MDS`) | every token tier: primitives (`DS.Theme.{Scale}Primitive`, `internal`), semantic and component definitions (`DS.Theme.SemanticTokens`, `DS.Theme.Components`), theme resolution to SwiftUI values, `mds` APIs, `@MDS`, scene setup, text size, components shared by every platform |
| MacDesignSystem | DesignSystem, AppKit | `DS` | what only macOS needs (e.g. AppKit tables, save panel) |
| PadDesignSystem | DesignSystem, UIKit | `DS` | what only iPad needs |
| PhoneDesignSystem | DesignSystem, UIKit | `DS` | what only iPhone needs |

- The platform targets extend `DS`, so a screen reads the same name on every platform; they exist only once they hold code.
- iPhone and iPad share the iOS SDK, so the compiler can't keep their targets apart: an iOS app depends on PadDesignSystem, PhoneDesignSystem or both, and a universal screen picks by size class.
- ImageIO is imported by DesignSystem only to decode image data (`DK.Icon.image`).
- DesignKit is platform-independent so Cores (Foundation only) build the data components render.
- All three tiers live in DesignSystem, so a theme's whole mapping is defined in one target. Primitives are `internal`: themes, semantic tokens and the token inventory read them; apps, Cores and the platform targets can't. Semantic and component definitions are DesignSystem types, since colors resolve as SwiftUI shape styles; their values are opaque, readable only through `mds`.

## 4. Token tiers
Following Figma's design-token architecture, three tiers, each referring only to the tier below:

| Tier | What | Example | Who uses it |
|---|---|---|---|
| Primitive | raw values: color ramps `{family}{step}` (step ≈ CIE L*) and the scales `space`, `size`, `radius`, `stroke`, `duration`, `opacity`, `fontSize` | `blue94`, `space16` | themes and amendments only, inside DesignSystem |
| Semantic | purpose: Colors (Background, OnBackground, Foreground, Border, Focus), Spacing, Typography, Radius, BorderWidth, Motion; each value an alias of a primitive: a color a light and a dark color primitive, each with an optional opacity primitive, plus an optional Increase Contrast pair of the same form; a macOS Typography style a `fontSize` primitive; Typography design a `Design` case, the one non-primitive token value | `Background.infoSubtle → blue94 / blue16` | components and screens through `mds` |
| Component | per-component configuration in `DS.Theme.Components`: aliases of semantic tokens, or `size` primitives for sizes | `InlineAlert.background(info) → Background.infoSubtle` | its component through `@MDS(\.{component})` |

- A component token exists only for a value that varies by the component's variant or belongs to it alone (its sizes, delays, spacing, radii); other values read semantic tokens. Themes and amendments are defined only in DesignSystem, so no client overrides a token, and adding a component token later is additive.
- A theme is a complete mapping: semantic → primitive and component → semantic. A missing value fails to compile; a literal where an alias belongs fails to compile.
- Built-in theme `standard`; an amendment overrides any subset of semantic or component tokens of one base theme with other primitives or aliases; at most one applies: amending an amended theme applies the new amendment to the unamended base theme, replacing the previous one.
- Colors resolve where they render (theme, color scheme, Increase Contrast pair when on); `mds` animations honor Reduce Motion.

## 5. Theme, scaling and access
- Access only through `mds`: view modifiers (`.font(mds:)`, `.foregroundStyle(mds:)`, `.background(mds:)`, `.border(mds:width:cornerRadius:)`, `.padding(mds:)`, …), `Color(mds:)`, `@MDS var mds`, `@MDS(\.{component})`; key paths are typed per group, so an unknown or misplaced token fails to compile.
- `.themeRoot(_:)` at every scene root and `.theme(_:)` at any depth inject the theme, tint and font design; `.themeRoot(_:)` also sets the page background as the window container background on macOS only, iOS and iPadOS keep system backgrounds; views without either render `standard`; replacing the theme restyles views in place.
- Typography: macOS uses the `fontSize` ramp scaled by text size; iOS and iPadOS use the system text styles with Dynamic Type, ignoring text size.
- Text size (`DK.TextSize`, seven steps 85–200 %; macOS only, iOS and iPadOS scale with Dynamic Type instead): `mds` fonts and text-bound component sizes scale with it; spacing, radii, border widths and durations don't.

## 6. Components
- Atomic levels: Atoms → Molecules → Organisms → Templates, each composing only lower levels; Pages are app screens.
- One component per file `DS+{Component}.swift`; it renders DesignKit data, wraps native controls, reaches tokens only through `mds`, and has light and dark previews.
- Native controls and system chrome kept (HIG, Liquid Glass); the theme drives content and tint.
- No gallery or catalog types in the library: the showcase apps hold them; the one exception is the `@_spi(Showcase)` token inventory in DesignSystem.

## 7. Showcase apps
- `ShowcasePhone`, `ShowcasePad`, `ShowcaseMac`, generated from `DemoApps/project.yml`, sharing `DemoApps/Shared/`.
- A `NavigationSplitView`: sidebar sections Foundations (Page anatomy, Primitives, Semantic tokens, Component tokens; each one file plus one catalog entry, content styled only through `mds`) and the atomic levels with their components; the detail shows the selected page.
- A component page: Playground (a control for each configuration property and the data it renders, plus theme, amendment, appearance and text size, with the live `DK.{Name}(…)` snippet), Variants (every variant, light and dark), Configuration (properties, component tokens and their aliases).
- The showcase apps are the manual verification surface of DesignKit specs.

## 8. Component lifecycle
Design System canvas: Prototype → Approved → spec (`docs/specs/components/{name}.md`) `Approved` → implemented in DesignSystem → showcase page → canvas status Implemented. A change to look or behavior goes through the canvas first.
